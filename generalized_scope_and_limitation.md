# 1.4 Scope and Limitations

This study covers the design, development, and prototype evaluation of a centralized, role-based, responsive Online Disaster Situation Report Generation and Record Management System. The platform is conceived as a configurable service for participating disaster risk reduction and management (DRRM) organizations rather than as a system permanently owned and administered by only one DRRMO. ZCDRRMO serves as the original study setting and may serve as the pilot organization, but each participating organization retains authority over its jurisdiction, users, reporting route, verification and approval decisions, records, disclosures, and official submissions. The technical operator maintains the service but does not acquire the statutory authority of an LDRRMO, local government, Incident Command System authority, or national agency.

## Technical Scope and Operating Environment

The proposed system will operate as a connected client-server web application. The presentation layer will use React and Tailwind CSS and will execute in a supported web browser on desktop computers, laptops, tablets, and internet-capable smartphones. Laravel and PHP will provide the server-side application layer for authentication, authorization, validation, workflow processing, report consolidation, SitRep generation, and audit-event recording. MySQL will provide persistent storage for organization profiles, users, jurisdictions, incident reports, verification decisions, generated SitReps, configuration versions, and audit records. Authorized attachments and generated files, where implemented, will be kept in protected server storage and linked to their corresponding database records.

During normal operation, an authorized user will access the system through an HTTPS address. The browser will display the functions allowed for the user's role, but permission will not depend only on hidden or visible interface controls. Every request to view, create, change, verify, approve, search, download, or export a record will be checked by the Laravel server against the authenticated user's account, organization, jurisdiction, assigned role, and permitted workflow state. The server will validate the request, read or write the appropriate MySQL records, preserve relevant audit information, and return an explicit success or failure response to the browser. Client-side validation may guide the user, but server-side validation and authorization will remain authoritative.

The system may run in a local development environment, such as XAMPP, Laravel Sail, Docker, or an equivalent configured environment, using test or de-identified data. This environment is intended for development and demonstration and will not be represented as the production host. Prototype evaluation may run on a controlled local-area server or approved hosted test environment. A pilot or operational deployment may run on a secured institutional server or contracted cloud infrastructure that supports the selected Laravel/PHP and MySQL versions, persistent storage, HTTPS, restricted administration, monitoring, backups, and restoration. Before the application can run in any deployed environment, its dependencies and compiled frontend assets must be installed, environment-specific configuration and secrets must be supplied outside the client code, the database schema must be created or migrated, persistent file storage must be configured, and the web service must be started and checked by an authorized technical administrator.

Users will not need a separate native mobile application because field and administrative functions will be delivered through the same responsive web application. Actual browser and device support will be limited to the operating systems, browser names and versions, screen sizes, network conditions, and assistive technologies included in the documented test matrix. Responsive layout means that the interface adapts to different screen sizes; it does not guarantee identical capability, speed, or usability on every device. Accessibility will be treated as a design and evaluation requirement using applicable WCAG 2.2 Level A and AA criteria for the implemented tasks, but the study will report only the browsers, devices, assistive technologies, methods, and criteria actually tested.

## Functional Scope

The system includes the User and Organization Management Module, Disaster Reporting Module, Disaster Report Verification Module, SitRep Generation Module, SitRep Catalog Module, and Dashboard Module. The prototype covers local reporting for floods, typhoons, and fires. Earthquakes, landslides, tsunamis, volcanic eruptions, non-disaster events, and other hazards are outside the present prototype. Support for another hazard requires separate requirements analysis, controlled terms and fields, workflow configuration, reference data, test scenarios, and approval before it can be claimed. The platform supports organization administrators, reporters, reviewers or verifiers, approvers, authorized viewers, records and privacy personnel, and limited technical support personnel. Actual role titles and escalation routes may be mapped during organization onboarding, but the system will not independently appoint a person to public office or confer government authority.

The User and Organization Management Module covers organization onboarding and basic configuration; account registration; authentication; activation, suspension, and deactivation; jurisdiction membership; role assignment; administrator handover; and access-event recording. Organization and jurisdiction identifiers will constrain server-side access to records, searches, attachments, dashboards, background actions, exports, and audit entries. For example, a purok reporter may submit an incident through the configured barangay workflow but may not verify the same report or generate and approve a SitRep unless separately authorized. Account deactivation will not erase the authorship, verification, or approval history attached to a government record.

The Disaster Reporting Module covers draft, submitted, corrected, and reconciled incident information. Records may include a stable identifier; hazard and incident description; organization and jurisdiction; location; occurrence, observation, receipt, and submission times; source channel; affected population; casualties; damage; immediate needs; actions taken; authorized attachments; and an explicit indication that a value is unknown, provisional, disputed, or not applicable. Initial reports may legitimately be incomplete while information is developing. The system will therefore preserve the distinction between an unavailable value and a confirmed zero. Automated validation will be limited to required-field, format, domain, range, consistency, workflow, and possible-duplicate checks. Passing these checks will not establish that the reported event or value is factually accurate.

The Disaster Report Verification Module covers triage, review, clarification, correction, corroboration, validation, partial validation where configured, return, rejection, and reconciliation. It will record the responsible actor, organization and role, time, source version examined, decision, and reason. Possible-duplicate and conflicting-value indicators will assist reviewers but will not automatically merge independent reports or determine which source is authoritative. Material corrections will create a new version or supersession relationship instead of silently replacing a submitted, verified, or approved record.

The SitRep Generation Module will retrieve only eligible report versions within the authenticated organization's authorized jurisdiction and reporting period. It will consolidate configured fields into a reviewable local SitRep and may identify the report stage, report number, reporting period, cut-off time, prevailing situation, preparedness measures, response actions, consolidated effects, issues and concerns, recommendations, included sources, unresolved discrepancies, template version, generated version, and approval state. Each sampled consolidated value should remain traceable to its source report version and verification decision. Automated generation will produce a draft for authorized human review; it will not by itself create an official national NDRRMC issuance or transmit a report to an external agency.

The SitRep Catalog Module will store generated and approved SitReps chronologically and by supported hazard category. Authorized users may search, filter, view, compare, download, correct, and supersede permitted SitReps while preserving earlier approved versions and their source relationships. A correction will not erase or overwrite the historical record on which an earlier decision was based. Exports may be saved to an authorized local device, but downloading a file does not constitute official submission to another agency.

The Dashboard Module will present descriptive summaries derived only from records the authenticated user is permitted to access. These may include incident counts, affected-population figures, report status, verification activity, SitRep coverage, processing time, and data freshness. Provisional and verified values will be distinguished, and relevant filters, reporting period, last update, missing values, and source records will remain available for interpretation. The dashboard supports monitoring of recorded information; it is not a forecasting, emergency-dispatch, public-warning, or automatic resource-allocation system.

The technical scope also includes persistent record storage, audit events for material actions, organization-controlled export, and backup and restoration procedures for the database and authorized files. Backups must be protected from ordinary user access and must be tested through restoration before recoverability is claimed. The exact backup schedule, retention period, storage location, recovery point objective, recovery time objective, upload limits, storage quota, server capacity, and support hours will be documented only after they are selected and tested. Audit records support accountability and traceability but will not be described as tamper-proof or legally conclusive unless those properties are separately engineered and evaluated.

The startup or designated technical operator will be responsible for deployment, server and database configuration, protected secrets, HTTPS certificates, application updates, monitoring, backup execution, restoration tests, technical incident handling, and authorized customer export or offboarding support. Each participating DRRM organization will remain responsible for validating users, assigning roles and jurisdictions, verifying incident information, approving SitReps, controlling disclosure, and applying its lawful records-retention and disposition rules. Any technical support access to customer records must be authorized, limited by purpose, scope, role, and duration, logged, and removed when the support activity ends.

## Limitations

The prototype remains a connected web system. It depends on compatible and adequately secured client devices, electrical power, internet or institutional network connectivity, DNS and HTTPS availability, the application server, the MySQL database, file storage, and trained authorized personnel. Weak or interrupted connectivity may delay page loading, attachment upload, submission acknowledgement, notifications, and dashboard updates. The interface may retain an unfinished form and support controlled retry where safely implemented, but the project does not include a native mobile application, full offline synchronization, SMS or radio fallback, satellite or mesh communication, or guaranteed operation during loss of power or telecommunications. ZCDRRMO and other participating organizations must retain approved telephone, radio, paper, face-to-face, or other contingency procedures for periods when the system cannot be reached.

The system does not autonomously determine whether an incident report is true; choose an authoritative source when reports conflict; declare a state of calamity; activate an emergency response; dispatch responders; allocate funds, relief, or personnel; issue evacuation orders; forecast hazards; perform predictive artificial intelligence; or publish official warnings to the general public. The absence of a digital report will not be treated as evidence that no disaster impact exists. Identity and account information may support an administrator's review, but the system does not independently prove a person's identity, office, or authority.

The prototype has no live integration with NDRRMC, OCD, DILG, DSWD, PAGASA, PHIVOLCS, GeoRiskPH, PhilSys, emergency hotlines, or another external government system unless a specific interface is later authorized, implemented, and tested. Stable identifiers, controlled terms, timestamps, geographic codes, schemas, and exports may support future interoperability, but they do not establish technical, semantic, organizational, or legal integration. Any future map, geolocation, email, push-notification, identity, or external-storage service will remain subject to its provider's availability, permission, accuracy, quota, security, and policy limits and will require separate failure handling and testing.

Prototype results will be limited to the declared source-code revision, software versions, server configuration, dataset, attachment profile, organizations, users, roles, browsers, devices, network conditions, concurrent workload, test procedures, and evaluation period. The study will not claim support for every browser or device, unlimited users or storage, a fixed response time, zero data loss, uninterrupted 24-hour availability, a production service-level agreement, national scalability, cybersecurity certification, legal compliance by software alone, or production readiness unless those qualities are supported by specific documented controls and tests. Functional completion, usability ratings, or a successful classroom demonstration will not by themselves prove procurement eligibility, commercial viability, nationwide suitability, improved disaster response, reduced casualties, or other public-safety outcomes.
