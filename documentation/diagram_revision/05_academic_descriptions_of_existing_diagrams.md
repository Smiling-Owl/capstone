# Academic Descriptions of the Existing System Diagrams

This document provides manuscript-ready descriptions of the twelve diagrams currently stored in `diagram_revision/diagrams`. The descriptions follow the explanatory style used in the earlier capstone manuscript: each discussion identifies the purpose of the figure, follows its decision paths and activities in sequence, and explains the records or system functions involved. The descriptions represent the diagrams as presently drawn and do not, by themselves, revise their process logic.

The figure numbers below retain the numbering already used in Chapter 1. Provisional subfigure letters have been assigned to the four account registration and management diagrams so that each image can be discussed separately without changing the numbering of the succeeding modules.

## Figure 1.1.2 Current Process of Purok-to-ZCDRRMO Incident Reporting and City Situation Report Preparation

*Figure 1.1.2* shows the current process of reporting disaster incident information from the Purok and Barangay levels to the ZCDRRMO Operations Department and the subsequent preparation of the City Situation Report. The process begins at the Purok level when an incident is observed. The Purok determines whether there is flooding in a flood-prone area, damage to infrastructure, or a condition that requires evacuation. If none of these conditions is present, the process ends. If a reportable condition is present, the Purok gathers the available location, time, effects, and urgent needs and notifies the Barangay through the existing communication channels.

Upon receiving the Purok notification, the Barangay checks the incident and prepares an initial report. The report is sent to the ZCDRRMO through SMS, telephone calls, online messaging, or another available channel. The ZCDRRMO Operations Department receives the initial report and sends a response team to the Barangay. It then checks whether the Barangay information is complete and internally consistent. When clarification or additional information is required, the ZCDRRMO requests clarification through the existing channel or sends personnel to gather data. The Barangay consequently gathers updated affected-population, damage, and response information, prepares an updated report, and sends it again to the ZCDRRMO. This creates a recurring exchange of updates until the available information is considered sufficient for consolidation.

Once the information is complete and consistent, the ZCDRRMO manually consolidates the messages, documents, shared drives, and spreadsheets received from the Barangays. The consolidated information becomes the basis for preparing the City Situation Report. The completed report is then submitted to the Office of the City Mayor, the Office of Civil Defense, and other applicable agencies. The figure therefore presents the current process as a largely manual and communication-dependent workflow in which clarification, field checking, consolidation, and report preparation are performed across several organizational handoffs.

## Figure 1.2.1 Proposed Barangay Disaster Situation Record Management and Situation Report Generation System Flowchart

*Figure 1.2.1* presents the general cross-functional flow of the proposed Barangay Disaster Situation Record Management and Situation Report Generation System. The figure brings together account registration, authentication, role identification, incident reporting, report verification, user management, dashboard access, Situation Report generation, and the Situation Report historical catalog. The process begins when the user opens the web application and proceeds to the application log-in page.

Before the user can continue, the system determines whether an account already exists. A user without an account is directed to the account registration process, while a registered user enters the required log-in credentials. The system checks the validity of the submitted credentials. Invalid credentials return the user to the log-in process or allow the user to end the session. Valid credentials proceed to account-type identification, which directs the user to the functions assigned to the Purok, Barangay, or DRRM Administrator side of the application.

The Purok side is directed to Purok Incident Reporting. Reports originating from this level move to the Barangay side for review through the Purok Incident Report Verification function. The Barangay side also provides Barangay Incident Initial Reporting and Purok User Management, reflecting the Barangay's responsibility to manage its Purok-level users and review information submitted from its jurisdiction. The DRRM Administrator side provides broader access to the system dashboard, system user management, Barangay Initial Report Verification, incident creation, Situation Report generation, and the Situation Report historical catalog. The figure therefore summarizes the proposed system as a role-routed workflow in which information progresses from local reporting functions toward city-level verification, consolidation, and record management.

## Figure 1.2.2.A Account Registration Flowchart

*Figure 1.2.2.A* shows the account registration process for Purok and Barangay users. The process begins through the M.1 connector and first determines whether the registering account is a Purok unit type. When the account is identified as a Purok account, the user provides the required Purok account credentials. When it is not identified as a Purok account, the registration proceeds through the Barangay account credentials path. Both paths converge at the account-verification decision.

The submitted registration information does not immediately become an active account. The system first checks whether the account has been verified by the authorized level of the reporting hierarchy. When verification has not yet been completed, the process displays a confirmation email message to inform the applicant of the required confirmation step or registration status. Once the account is verified, the system records the user's account information, assigned type, and status in the Accounts Database. The figure therefore establishes registration as a controlled process rather than unrestricted account creation, with the account type and verification status determining whether the submitted credentials are stored as a confirmed system account.

## Figure 1.2.2.B Admin User Management Flowchart

*Figure 1.2.2.B* presents the Admin User Management process of the proposed system. The process begins through the M.1 connector and checks whether the current account is a DRRM Administrator account. If the account does not possess the required administrator type, the system denies access to the Admin User Management page. This decision serves as the initial role restriction for functions that can create or view higher-level system accounts.

When the account is identified as a DRRM Administrator, the process determines whether a new DRRM Administrator account will be created. If no new account is required, the user is directed to the list of existing accounts. If account creation is selected, the authorized administrator creates a ZCDRRMO account and supplies the corresponding account details. These details are stored in the Accounts Database. The registered account information is subsequently retrieved and included in the displayed list of existing accounts. The figure therefore shows that account creation and account viewing are connected administrative functions and that the Accounts Database acts as the central source of registered user information for the management interface.

## Figure 1.2.2.C Purok Account Verification Flowchart

*Figure 1.2.2.C* shows the process for reviewing and verifying a Purok account registration. The process begins through the M.1 connector and checks whether the reviewing account is a Barangay unit type. This reflects the hierarchical relationship in which the Barangay is responsible for reviewing registration requests originating from its Puroks. Accounts that do not follow the required reviewing role are routed to the permission-related page response, while an authorized Barangay account is allowed to display the pending Purok registration request.

After the registration request is displayed, the Barangay reviewer examines whether the submitted Purok registration credentials are valid and correct. If the details cannot be validated, the Purok registration is rejected and a reason for the rejection is recorded or communicated. If the details are accepted, the system verifies the account, confirms its creation, and stores the resulting account status in the Accounts Database. An account-verification notification is then sent to communicate the successful decision. The figure therefore places the Barangay between Purok registration and system activation, ensuring that a Purok account is reviewed by the organizational level responsible for that local jurisdiction before it is confirmed.

## Figure 1.2.2.D Barangay Account Verification Flowchart

*Figure 1.2.2.D* illustrates the account-verification process for Barangay registrations. The workflow begins through the M.1 connector and determines whether the reviewing user is an Administrator unit type. Users who do not have the required administrator role are routed to the permission-related page response. When the role requirement is satisfied, the system displays the Barangay registration request for administrative review.

The Administrator examines whether the submitted registration credentials are valid and correct. When the credentials do not meet the verification requirements, the Barangay registration is rejected with a corresponding reason, after which the workflow returns through the M.1 connector. When the credentials are accepted, the system verifies the account, confirms its creation, and records the verified account in the Accounts Database. The system also sends an account-verification notification before returning to the main process through M.1. The figure therefore presents Barangay registration as a higher-level approval process in which the DRRM Administrator controls the activation of Barangay accounts that will participate in incident reporting and the review of Purok submissions.

## Figure 1.2.3.A Proposed Purok-Level Incident Reporting Module Flowchart

*Figure 1.2.3.A* shows how the Incident Reporting Module is facilitated at the Purok level. The process begins through the M.1 connector and determines whether there is a request to update an existing Purok Incident Report. If an update request exists, the authorized user modifies the incident report information through version control. The modified report details and their corresponding version are then stored in the Purok Incident Report Database. This path allows the system to retain the updated form of the report while identifying the version associated with the modification.

When there is no update request, the process determines whether the user intends to create a new incident report instance. If a new report is required, the user creates the Purok Incident Report and supplies its report details. The submitted information is saved in the Purok Incident Report Database. If the user does not create a new report, the module proceeds directly to the report-history view. Both newly created and modified records are made available through the Purok Incident Report History. The figure therefore represents the Purok module as the initial reporting and record-maintenance point of the system, supporting the creation, versioned modification, storage, and historical viewing of incident reports originating from the community level.

## Figure 1.2.3.B Proposed Barangay-Level Incident Reporting Module Flowchart

*Figure 1.2.3.B* illustrates the logic of incident reporting at the Barangay level. The process begins through the M.1 connector and first determines whether there is a request to update an existing Barangay Incident Report. When an update is required, the Barangay modifies the report information through version control, submits the modified report, and stores the modified report details and version in the Barangay Incident Database. This path allows continuing disaster information to be reflected in a later record while maintaining a version reference.

If there is no Barangay report update request, the system checks whether Purok Incident Reports are available. When no Purok reports are available for processing, the Barangay may view the existing Purok Incident Report History. When reports are available, the Barangay evaluates whether the submitted Purok Incident Reports are verified and correct. Reports that require correction are returned through a notification to the responsible Purok. Reports that satisfy the review condition are consolidated by the Barangay.

After consolidation, the Barangay submits a Barangay Incident Report containing the combined report details and corresponding version. The resulting record is stored in the Barangay Incident Database. The figure therefore gives the Barangay a dual function: it acts as the reviewer of Purok-level reports and as the reporting unit that consolidates accepted local information into a Barangay-level incident record for the next stage of the system.

## Figure 1.2.4 Proposed Disaster Report Verification Module Flowchart

*Figure 1.2.4* presents the Admin Incident Report Verification process for Barangay Incident Reports received by the city-level system. The workflow begins through the M.1 connector and checks whether new Barangay Incident Reports are available. When a new report is present, it proceeds to the verification decision. When no new report is available, the system checks whether there is a notification concerning a modification to an existing Barangay Incident Report. A modified report is also returned to the verification decision, while the absence of both a new report and a modification notification directs the authorized user to the existing Barangay Incident Reports.

At the verification decision, the authorized personnel determine whether the Barangay Incident Report is verified. A report that does not satisfy the verification condition results in a modification request being sent to the Barangay. This returns the report to the originating level so that the required information can be corrected or completed. A report that satisfies the verification condition is consolidated, and its report data and version are stored in the Barangay Incident Report Database. The same database supplies the records shown in the existing-report view. The figure therefore represents verification as a recurring review process that covers both new and modified submissions and connects an unsuccessful review to a correction request before the report is accepted for consolidation and storage.

## Figure 1.2.5 Proposed Situation Report Generation Module Flowchart

*Figure 1.2.5* shows the Situation Report Generation Module of the proposed system. The process begins through the M.1 connector and determines whether there is a current Situation Report update. This decision separates the creation of a new Situation Report from the modification of an existing report.

When no current update is being processed, the system consolidates the available Barangay Incident Reports. The consolidated Barangay incident information and its version become the basis for creating a new Situation Report. The newly created report is then stored in the Situation Report Database. This path represents the initial preparation of a Situation Report from the Barangay-level information available to the system.

When the process identifies a current Situation Report update, the system retrieves the related Barangay Incident Reports. The updated Barangay incident-report data are used to modify the current Situation Report and assign its updated version. The revised report is then stored in the same Situation Report Database. The figure therefore treats Situation Report preparation as a continuing process: a report may first be created from consolidated Barangay records and may later be updated when related incident information changes, with the database serving as the repository of the resulting report versions.

## Figure 1.2.6 Proposed Situation Report Catalog Module Flowchart

*Figure 1.2.6* shows the Situation Report Catalog Module of the proposed system. The process begins through the M.1 connector and directs the authorized user to the Situation Report viewing function. The Situation Report Database supplies the available Situation Reports to this interface, allowing the user to access the reports that have already been generated and stored by the system.

From the report-viewing function, the user may proceed to the Situation Report History. The database also provides the Situation Report version data required to present the historical sequence of a selected report. The distinction between the general Situation Reports output and the Situation Report Versions Data indicates that the catalog is intended to provide both access to the current report records and access to the versions associated with their development over time. The figure therefore presents the catalog as the retrieval and historical-viewing component of the proposed system, using the Situation Report Database as the common source for the report list and its version history.

## Figure 1.2.7 Proposed Dashboard Analytics Module Flowchart

*Figure 1.2.7* shows the role-based Dashboard Analytics process of the proposed system. The process begins through the M.1 connector and identifies the account type of the current user. The first decision checks whether the account is a Purok unit type. When this condition is satisfied, the system displays the Purok Dashboard Page using Purok Incident Report data retrieved from the Purok Incident Report Database.

If the account is not a Purok account, the process checks whether it is a Barangay unit type. An identified Barangay account is directed to the Barangay Dashboard Page, which receives Barangay Incident Report data from the Barangay Incident Report Database. If the account is neither Purok nor Barangay, the system checks whether it is a DRRM Administrator account. Accounts that do not match any authorized type are denied access to the dashboard pages.

The DRRM Administrator Dashboard presents a broader collection of system information. The figure shows affected-population data, incident data, and Situation Report data being made available to the administrator interface, with the Situation Report Database serving as the source of the Situation Report information and related analytical data. The dashboard therefore varies according to the account's assigned level: Purok users receive a localized view of Purok reports, Barangay users receive a view of Barangay reports, and the DRRM Administrator receives a wider operational overview. This role-based separation is intended to limit the displayed information to the functions and reporting level associated with the authenticated account.
