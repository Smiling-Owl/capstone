# Relational Data Model derived from the supplied ERD

This is the RDM: each entry defines a relation (table), its attributes, generic data types, and keys. It lists the schema directly instead of drawing relationship connectors. The separate DBML file is for tools such as dbdiagram.io that render a relationship diagram.

[Open the interactive schema workbench](rdm_schema_workbench.html) to move tables, choose a layout, and inspect their connections. The [static connected RDM](erd_derived_rdm_all.svg) remains available for a single-page overview of all 32 relations.

Column markers: `[PK]` = primary key; `[FK → relation.column]` = foreign key. A column can carry both markers for a subtype relation.

## Source transcription and assumptions

- The model includes the 32 entity boxes in the supplied image: 15 account, hazard, profile, and verification relations; 7 incident-report relations; and 10 situation-report relations.
- Every child connected by `includes` has an FK to its visible parent. The source relationship endpoints are partly crossed or lack fully legible cardinality marks, so parent-to-child `1:N` cardinalities are inferred from the inclusion meaning.
- Both `D` subtype groups use the parent key as the subtype PK and FK. Account creation lines are represented by `created_by_*_account_id`; account-to-profile and account-to-hazard lines are represented by their corresponding FKs.
- The verification boxes retain their relationship to the verified profile or incident report and gain `reviewer_account_id` to represent the reviewer field. This normalized FK name is used even where the source only says `reviewer`.
- The line that may connect Situation Report and Incident Report has an ambiguous endpoint, so the model records this as unresolved and leaves out that FK.
- The duplicate `Hazard_type` is stored once. The empty `Situation_report_lifeline-status_` row is omitted. The five fields inside the lifeline-status box that carry `Situation_report_damage-assessment_` prefixes in the source remain under `situation_report_lifeline_status`; the box placement and field prefix conflict is a source inconsistency.
- `account_name` and the first/middle/last-name columns are all preserved as drawn, even though they may overlap. Component table/column names remain source-based, with hyphens, spaces, and punctuation normalized to snake_case. The casualty-summary table keeps its source's `affected_casualty` ID and attribute wording.
- Fields whose source names imply dates, times, quantities, counts, or amounts use generic `date`, `datetime`, `int`, or `decimal`; descriptive text uses `text`; remaining values use `varchar`. No lengths, precision, nullability rules, enum sets, defaults, indexes beyond keys, or deletion rules are inferable from this paper ERD. Refined physical types and constraints belong in the implementation model.
